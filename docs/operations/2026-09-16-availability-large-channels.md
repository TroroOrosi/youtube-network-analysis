# サイト障害・大規模チャンネル収集の修正と本番確認

## 確認できた事実と未確認事項

- 2026-09-16 20:45:31 JST、GitHub Actions から認証情報・Cookie を送らず、
  本番 `/login` にアクセスしたところ HTTP 500（0.229 秒）だった。
  証跡: Actions run `35092027850` / job `104780345488`。
- この確認はサイトの障害を示すが、Cloud Run の起動例外、保存先の障害、
  IAM、リソース不足などのどれが本番の直接原因かはまだ特定していない。
  本作業では本番ログ・設定・保存データに対する認証済みアクセスはない。
- 旧コードでは、コメントの別ページに同じ投稿者が現れると公開処理が
  重複エラーになり、収集が RUNNING のまま残る不具合を再現した。
- 単一動画内のページ取得で実行時間を区切れず、日次枠を超える動画では
  翌日も同じページを取り直し、完了できない経路を再現した。
- 旧 Firestore 保存処理は分割文書をすべて一度に送信した。
  JSON エスケープを含む 10 MiB 超のリクエストが拒否されるテストで再現した。
- この変更はコード修正であり、本番へのデプロイ・実チャンネルでの成功を
  示すものではない。デモの成功を実データの成功として扱わない。

## 修正内容

### 収集と再開

`collection_jobs` は取得ページ単位で投稿者を集約し、コメント件数を加算、
最終投稿時刻を最大値にする。動画・登録者の重複 ID は先に取得した行を残す。
全種類のページ取得で、次の API 呼び出しの前に時間枠を確認する。
時間切れのスライスは次ページの位置と最小限の行データを保存して QUEUED に戻る。
実行中の API 呼び出しと保存処理が時間枠を越える可能性は残る。

コメント収集は日次枠を超えても、その動画の取得済みページを保持する。
新しいページの取得を進捗に数えるため、単一動画が複数日にまたがっても、
進んでいる収集を「3 日間停止」と誤判定しない。
**登録者・動画一覧の日次枠到達時は、既存の PARTIAL 終了方針を変更しない。**
これらは時間枠による中断には対応するが、日次枠を超える全件収集には別途運用設計が必要。

未完了の候補を完成済みの分析データとして公開しない。予期しない例外は
呼び出し元に返すとともに FAILED とし、消費済みページ数・API 使用量を残す。
旧データの RUNNING は起動時に FAILED にする。途中の公開状態が不明なため、
自動で再実行せず、履歴確認後に利用者が新規収集を開始する。
取消・終了・ワークスペース削除時はチェックポイントを除去する。

### 保存と画面

Firestore の単一要求は最大 8,000,000 バイト・200 書き込みに抑える。
文書片は従来どおり最大 900,000 UTF-8 バイト。大きい状態は一意な世代の
文書片を先に保存し、最後に小さな参照元文書を原子的に切り替える。
全体の SHA-256 を読み込み時に検証する。
途中保存の失敗では前の正常な状態を維持し、保存成功後の古い文書片の
削除失敗を「保存失敗」と誤報告しない。応答消失時は参照先を確認する。
起動時の読み込み不良を無視して空の状態に置き換える処理は追加していない。

稼働中の保存先エラーには、日本語の HTTP 503 と `Retry-After: 60` を返す。
この例外処理は、アプリ生成前の起動例外を回復するものではない。
ブラウザーの収集処理は 429/503 のときだけ最大 5 回の待機・再試行を行う。
権限・CSRF エラーや応答不明の通信切断では、盲目的に POST を繰り返さず、
読み取り専用の進捗ページを開き直すよう案内する。
認証、CSRF、OIDC、API 利用枠、公開登録者などの取得制約は維持する。

## 本番反映前の必須事項

**ストレージ移行を伴う。旧リビジョンへの単純なトラフィック切戻しは安全ではない。**

1. 認証済みの管理 PC から、現時点のリビジョン、サービスの状態と ERROR ログを確認。
   下記は読み取り専用。秘密値・生の利用者データを PR やチャットに貼らない。
2. ログに基づき、保存先の到達性・権限・容量・起動エラーを切り分ける。
   保存データや接続を削除して「復旧」させない。認可のやり直しが必要な場合のみ、
   利用者本人が Google の同意画面で実施する。
3. 収集の新規開始と Scheduler を停止し、実行中のスライスを終了させる。
   ユーザーアクセスも制限し、旧インスタンスが状態を書かないことを確認する。
   モジュール全体をメモリーに保持する単一ライター設計なので、
   **旧・新リビジョンが同じ保存先に書くカナリア展開はしない。**
4. 五つの状態文書と全参照文書片を、アクセス制限された保存先に整合した形で退避。
   資格情報は Secret Manager に残し、ソースや CI に書き出さない。
   バックアップ・復元の権限、費用、手順を管理者が確認する。
5. 必要なら本番とは別の検証用保存先で復元検証。新コードは jobs snapshot v1 を読めるが、
   書き込みは v2 になる。大容量状態は新しい Firestore 世代形式になる。
   **旧コードはどちらも読めないため、旧コードへ戻すなら書き込みを止め、
   整合した旧形式の全モジュールを復元する必要がある。**
   バックアップ後の更新を失う可能性がある。原則は新形式対応コードでの修正を優先。
6. 一つのリビジョン・一つのプロセスで新コードを起動。既存環境変数、IAM、
   Secret Manager 参照、Firestore 参照を維持する。インスタンス数を増やして解決しない。
7. `/login` が 200、未ログイン `/` がログインへ遷移、認証なし `/internal/drain` が拒否、
   セキュリティヘッダーが維持されていることを確認。
8. 本人の認証で対象チャンネルを確認してから、一つの収集を明示的に開始。
   履歴、増加するページ数、日次枠待ち、再開後の取得位置、分析の準備状態を確認。
   実チャンネルの分析が完成し、ERROR/5xx の再発がないことをもって復旧判定する。
   Scheduler の有効化は単一ライター状態を確認した後に行う。

```powershell
gcloud run services describe yna-web --project snappy-byway-498603-v9 --region asia-northeast1 --format="yaml(status.conditions,status.latestReadyRevisionName,status.traffic)"
gcloud run services logs read yna-web --project snappy-byway-498603-v9 --region asia-northeast1 --freshness=1d --limit=100 --log-filter="severity>=ERROR"
```

大規模向けの「無制限」保証ではない。全体 JSON のメモリー保持・全体シリアライズ、
Firestore の読み書き費用、単一ライター制約は残る。失敗した文書片の削除や
途中で強制終了した場合には、参照されない世代が残ることもある。
自動的な無差別削除を行わず、稼働を止めた状態で全参照元を確認して整理する。
